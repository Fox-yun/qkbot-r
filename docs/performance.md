# 本地性能冒烟实测

性能测量用于了解成本与定位异常，不设置固定内存验收门槛。功能完整和可靠性优先于压低 RSS；按用途提高上下文、记忆容量或插件负载造成的合理增长可以接受。

本报告是记忆容量可配置、长历史及更多工具轮次调整前的基线，构建身份以样本中的 SHA-256 为准。它不代表后续每次代码修改后的重新测量结果。

2026-10-19 对同一个发布版做了两次本地冒烟测量：空闲工作集为 **9.42–15.68 MiB**，两个群并发处理 20 条消息时的采样峰值为 **10.27–16.12 MiB**。这说明当前实现的基础占用较小，也说明短测工作集会在运行间变化；它不是实际 QQ 环境的容量上限。

以下为最后一次运行的完整指标。第二次运行修正了偶数条延迟的中位数计算；第一次内存指标未受影响，一并保留以避免只报告较低值。

| 项目 | 实测 |
| --- | ---: |
| 空闲工作集，3 次采样中位数 | 9.42 MiB |
| 负载期间工作集采样峰值 | 10.27 MiB |
| 负载期间私有提交内存采样峰值 | 2.32 MiB |
| 进程自身 CPU 时间增量 | 0.05 秒 |
| 输入 / 成功发送回复 | 20 / 20 |
| 模型 HTTP 请求次数 | 20 |
| 负载总耗时 | 5.105 秒 |
| 单条消息延迟中位数 / P95 | 508.42 / 522.38 毫秒 |
| 发布版可执行文件 | 9,570,304 字节，约 9.13 MiB |

工作集来自 Windows `WorkingSet64`，包含共享驻留页；私有提交内存来自 `PrivateMemorySize64`，两者不是同一指标。CPU 是机器人子进程的累计处理器时间增量，不是整机利用率。占用统计不包含测量脚本、PowerShell、QQ 客户端或 Milky。

## 复现条件

- Windows x64，系统构建 `10.0.26200`，20 个逻辑处理器；使用 `cargo build --release --locked` 构建。
- 两个本地模拟群同时对话，每群 10 条；每群收到上一条回复后再发送下一条，因此没有刻意压满队列。
- 实际启动机器人并经过 Milky WebSocket 接收、SQLite、上下文组装、模型 HTTP、发送账本及 Milky HTTP 确认。
- Milky 和模型均由 Node 内置库在 `127.0.0.1` 模拟。模型每次固定等待 **500 毫秒**，返回简短文本；延迟读数包含这段等待。
- 启用 AI 和时钟，提醒关闭；输入预算 6000、近期消息 24 条，长期记忆初始为空；测试期间不触发后台整理或工具执行。仅此测试把发送冷却设为 0。

在完成发布构建后运行：

```powershell
node scripts/perf-smoke.mjs
```

脚本会创建 `target/perf-smoke/` 下的独立配置与数据库，隐藏启动机器人子进程，记录空闲和负载样本；不读取生产配置，也不连接真实 QQ 或模型接口。结束后终止这次隔离测试进程，保留原始测量文件。最新结果写入 `target/perf-smoke/latest.json`。

本次的[完整样本](performance-sample.json)保留逐次采样、逐条延迟、前次内存观察、平台信息和可执行文件 SHA-256，已去除本机绝对路径。中位数使用中间两条延迟的平均值，P95 使用排序后的第 19 条。

## 如何解读

这次短测确认了程序能用较小基础内存完成真实代码路径上的双会话聊天。真实服务还会增加 TLS、较长请求与响应、长期记忆检索、后台摘要、工具及插件负载；网络和模型处理时间通常也是回复延迟的重要部分。

本次没有测量长期运行后的碎片、数据库持续增长、达到队列上限的压力、故障重连或数十个活跃群。不能把 16.12 MiB 当作固定上限，也不能据此承诺某台机器可以服务多少群。部署后应分别观察机器人、QQ 与 Milky 的进程占用，再按实际输入长度和并发调小或调大资源上限。

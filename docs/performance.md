# 新版性能实测

2026-10-20 使用同一份 Rust 功能代码、全部 12 个原生插件，完成 Windows 原生进程与 Linux Podman 容器内进程的隔离测试。Linux 的初始 RSS 为 **15.05 MiB**，聊天峰值 **16.33 MiB**，绘图和记忆流程后空闲 **53.95 MiB**。Windows 两次运行对应为 **11.54–11.60 / 13.61–13.64 / 34.67–34.90 MiB** 工作集。

两边都实际完成 32 次发送、工具调用、提醒增查删、4 张 PNG，以及两个群的摘要、长期记忆写入和召回。数字是这些条件下的观察，不是生产上限或容量承诺；功能完整和可靠性优先，不设置 RSS 验收门槛。

| CPU / 宿主可见内存 | 2 个逻辑 CPU，AMD EPYC 7K83 标识，1.90 GiB | 20 个逻辑 CPU，Ryzen AI 9 H 365，29.79 GiB |

| 内存口径 | 机器人宿主 HPID 的 `/proc` VmRSS | 机器人 `WorkingSet64` |
| 完整样本 | [Linux，520 次采样](performance-podman-sample.json) | [Windows，236 次采样](performance-sample.json) |

每个模拟模型请求固定等待 **500 ms**。普通聊天用一次请求，时钟工具用两次；不能据此推算真实模型速度。回复延迟从模拟入站消息写入 WebSocket 开始，到模拟协议端收到文本、读取完图片为止；发送账本是否最终确认另外核验。

CPU 是该进程跨核累计时间，不是整机利用率。大量墙钟时间在等待模型和后台维护，因此不能用全程平均值代替突发计算需求。短阶段受计时粒度影响，显示 0 不代表没有计算。CPU 截至最后一次资源采样，随后停止进程与数据库检查点未计入；脚本总墙钟时间则包含收尾。

启动读数包含脚本准备配置、端口，以及容器模式的镜像检查和 Podman 启动，不是单独的机器人启动耗时。首次管理员密码设置也实际执行。生命周期峰值包含初始化和绘图的短时分配，可能高于周期采样峰值。采样每轮为 250 ms 加资源查询时间，原始时间戳已保留。

Windows 的初始私有提交内存采样峰值为 2.71 MiB，聊天期间为 3.36 MiB；这是 `PrivateMemorySize64`，与包含共享页的工作集不能相加。Linux 样本没有将 RSS 或 `statm` 估算伪装成同一种私有提交量。

## 图像、工具与记忆路径

全部 12 个原生插件均由运行状态确认加载，同时启用 AI、时钟、提醒和 Web 管理。NoneBot 外部服务关闭；没有启动 Python、浏览器或真实 QQ。实际图像测试包含字体/词库加载、绘图、PNG 编码和模拟协议端下载受控的本机临时媒体 URL。

| 操作 | Linux 请求到图片读取完成 | Windows 请求到图片读取完成 | 尺寸 |
| --- | ---: | ---: | --- |
| 首次 Wordle 开局 | 12.26 ms | 25.75 ms | 900 × 645 |
| Wordle 猜词，字体已加载 | 47.90 ms | 16.07 ms | 900 × 645 |
| 签到日历 | 44.90 ms | 13.03 ms | 900 × 650 |
| 菜品菜单 | 58.47 ms | 31.04 ms | 900 × 2884 |

这些各只有一次操作，不是图像延迟 P95。Linux 图片分别为 14,390、16,542、46,706、291,829 字节；Windows 为 14,496、16,651、47,096、302,681 字节。菜单采用真实内置菜单的文字列表绘图，没有下载外部食物图片。首次绘图后增长包含中文字体、词库及分配器保留空间，不应仅用启动空闲值估算有图片功能的服务。

两套 SQLite 与发送账本都核验得到：32 条发送全部 `confirmed`，2 次时钟工具成功，1 条提醒经历创建、查询、取消，1 个 Wordle 局面，151 个菜单条目。两个群各产生 1 条带原文证据的长期记忆和 1 份摘要，随后各一次请求确实带入召回文本；提取文本专门与原始聊天、摘要区分，防止把历史命中误报为长期记忆召回。

后台维护保持生产的 **60 秒周期、每轮一个会话**，测试将空闲触发改为 30 秒。整理等待阶段为 Linux 108.90 秒、Windows 102.37 秒，各仅有 2 个等待 500 ms 的模型请求，阶段时间主要在等调度。受控 JSON 验证了真实提交、证据校验、索引召回和上下文路径，没有评价真实模型的记忆准确率。

## 复现与容器验收

脚本只用 Node 内置模块，需要 Node 22.13+。先构建 release，再运行：

```powershell
node scripts/perf-smoke.mjs --binary target/release/qkbot.exe --output target/perf-smoke/windows.json
```

本次 Windows 二进制位于 `target/reliability-check/release/qkbot.exe`。Linux 原生进程可将 `--binary` 指向 Linux release；已有 Podman 镜像时运行相同工作负载：

```sh
node scripts/perf-smoke.mjs --container-image localhost/qkbot-r:latest --output target/perf-smoke/podman.json
```

将镜像名替换为实际构建的标签；本次用 `podman-test`。容器模式使用 host 网络，`keep-id` 将独立测试目录映射给容器 UID/GID 10001，直接启动镜像内二进制及合成配置。资源采样由 `podman top hpid` 获取机器人宿主进程 ID，再读取 `/proc`，不是 `podman stats` 的 cgroup 口径。结束仅移除本次随机命名的容器。

脚本在 `target/perf-smoke/` 下创建独立配置、认证文件、媒体和 SQLite，选随机本机端口，清除继承的 `QKBOT_*` 凭据及代理覆盖，使用合成凭据；不读取生产配置，不连接真实模型/QQ，也不使用现有 3210 服务。双群各 10 条顺序聊天、两群并发，模型并发上限 2，输入/输出预算 6000/800、近期消息 4 条、后台输入/输出预算 6000/1600；发送冷却仅在基准中设为 0。通常约两分钟，主要等实际后台调度，最后停止并检查本次子进程，保留合成数据及 JSON。

性能脚本直接提供配置，没有测试部署入口的首次初始化。另行运行的 [容器验收脚本](../scripts/container-smoke.py)已通过实际入口、UID 10001、中文字体、`--check`、首次配置初始化且不覆盖既有配置、管理员凭据重启持久化、SIGTERM 退出码 0，以及停机后卷导出数据库完整性检查；这些属于功能验收，未冒充性能样本。

## 测量边界

所有资源数字仅包含机器人进程。Node 模拟器、PowerShell 采样器、QQ/Milky、真实模型、NoneBot/Python/浏览器、Podman 运行时与虚拟机均未计入。镜像包含中文字体等运行文件，其磁盘体积不等于工作集。Linux 与 Windows 的驻留统计也不能直接代替整台机器的部署预算。

本次没有压满队列，没有测真实网络插件、外部图片下载、长响应、大数据库、长期碎片、断线重连或故障压力。全部插件加载不等于全部插件都经过性能测试。部署预算需另计 QQ 协议端和可选 Python/浏览器；按实际输入长度、图像尺寸及并发观察增长，不能把 53.95 MiB 或 46.07 MiB 当成生产内存硬上限。
